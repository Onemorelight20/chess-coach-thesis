# Метод підбору тренувальних задач на основі інтерпретації прогнозу шахового рейтингу

Explainable ML-метод, що оцінює рейтинг Elo шахіста за його партіями (без доступу
до реального рейтингу), інтерпретує цей прогноз і за відхиленням внесків ознак від
типових для гравців того самого рівня визначає напрями тренування — виключно на
основі аналізу рушієм Stockfish, без нейромереж (Maia тощо) чи сторонніх моделей
людської гри.

```
PGN → Stockfish (MultiPV) → вектор із 29 ознак → XGBoost (Elo) → SHAP, нормований
за рівнем гравця → 3 напрями тренування → Streamlit (задачі Lichess)
```

## Конвеєр

1. **Збір даних** (`src/data_layer/collector.py`) — стратифікована по рейтингу
   вибірка партій з Lichess Open Database, окремо на кожен пул часового
   контролю (bullet/blitz/rapid/classical), оскільки Elo і ACPL не порівнювані
   між пулами.
2. **Аналіз рушієм** (`src/engine/analyzer.py`) — Stockfish з MultiPV=5 оцінює
   кожну позицію партії: втрату центіпішаків відносно найкращого ходу, ранг
   зіграного ходу серед кандидатів рушія, критичність позиції.
3. **Вилучення ознак** (`src/features/extractor.py`) — 29 ознак на партію:
   точність по фазах, ситуативна точність, win-probability-зважена точність,
   тактико-позиційні сигнали, керування часом, engine-agreement.
4. **Агрегація** (`src/features/aggregate.py`) — усереднення вектора ознак по N
   партіях гравця (single game — зашумлений зріз навички, див.
   [aggregation curve](#ключові-наукові-знахідки)).
5. **ML-прогноз** (`src/ml/model.py`) — окрема модель XGBoost на кожен пул
   передбачає Elo з агрегованого вектора.
6. **XAI** (SHAP, `src/ml/model.py`) — розкладає прогноз на внески ознак, після
   чого визначає напрями тренування. Це **не** сирий `argmin`: внески спершу
   нормуються на їхнє типове значення для гравців того самого прогнозованого
   рівня (`build_shap_reference.py`), а кандидатами є 17 ознак із 29 — ті, яким
   відповідає тренувальна тема. Повертається шортліст із k = 3 напрямів.
   Обґрунтування обох поправок і виміряна ціна — знахідка 4 нижче.
7. **Рекомендація** (`src/ml/recommender.py::get_plan`) — по задачі Lichess на
   кожен напрям, з рейтингом, близьким до прогнозованого Elo; повторювані теми
   схлопуються, бо кілька ознак можуть вести на ту саму тему.
8. **Інтерфейс** (`app.py`) — Streamlit: завантаження PGN або пошук партій за
   ніком (Lichess/Chess.com), вибір партій, аналіз, візуалізація SHAP,
   рекомендація.

## Дані

Партії — з публічного дампу Lichess (`lichess_db_standard_rated_2026-01.pgn`).
Наївний збір (найактивніші гравці) дає вибірку, зміщену до середнього рейтингу:
у старому датасеті (`data/legacy/`) лише **1.4%** партій належали гравцям з
рейтингом <900. Це напряму спричиняло помилкове передбачення: гравець з
реальним рейтингом ~700 отримував прогноз ~1600 (докладніше —
[Каліброваційна знахідка](#ключові-наукові-знахідки)).

Виправлення — стратифікований збір (`collector.py --stratified`): гравці
вибираються рівномірно по бінах рейтингу 200 Elo в діапазоні **400–2800**, а не
за активністю. Основні датасети (`scripts/collect_2k.sh`, ~2000
гравців/пул, до 8 партій/гравця):

| пул | рядків | гравців | діапазон Elo |
|---|---|---|---|
| bullet | 16 413 | 2056 | 400–3016 |
| blitz | 17 234 | 2160 | 400–2806 |
| rapid | 15 949 | 1998 | 400–2932 |
| classical | 10 112 | 1270 | 531–2795 |

Збір **резюмований**: `src/data_layer/collector.py` пише чекпойнт кожні 200
партій (`<output>.parquet.partial`); перерваний запуск `bash
scripts/collect_2k.sh` продовжується з чекпойнта, а не з нуля.

## Ознаки (29)

`src/features/extractor.py::FEATURE_NAMES`, три групи:

1. **Базові (21)** — точність (ACPL, inaccuracy/mistake/blunder rate), точність
   по фазах (opening/middlegame/endgame), ситуативна точність
   (conversion/defense ACPL), стиль (engine-match rate, capture/check rate),
   тактико-позиційні сигнали (hanging pieces, king danger, mobility, center
   control, material volatility, pins), керування часом (think-time
   consistency/avg/time-pressure).
2. **Win-probability (3, `wp_*`)** — втрата ймовірності виграшу за хід
   (логістична модель Лічесс/Maia **застосована до оцінки Stockfish** — формула,
   не нейромережа), частка "блондерів" за критерієм ≥10% втрати ймовірності,
   консистентність втрат (`cpl_std`).
3. **Engine agreement (5, MultiPV)** — частка ходів, що збігаються з
   найкращим/топ-3 ходом рушія (`top1_agree`, `top3_agree`), середній ранг
   зіграного ходу (`avg_move_rank`), точність і збіг з найкращим ходом саме в
   "критичних" позиціях, де є єдиний явно найкращий хід (`acpl_critical`,
   `critical_agree`).

Кожна ознака має записану **орієнтацію** (`FEATURE_ORIENTATION`: чи "більше" —
це "гірше" чи "краще"), що критично для коректного визначення слабкості на
основі сирих значень ознак (див. [нижче](#ключові-наукові-знахідки)).

## Моделі та метрики

Player-grouped 5-fold CV (гравець ніколи не потрапляє одночасно в train і
test), XGBoost (`n_estimators=300, max_depth=5, learning_rate=0.05`), окрема
модель на пул (`results/pool_summary.csv`, `src/ml/models/*_metrics.json`):

| пул | MAE (Elo) | RMSE | R² |
|---|---|---|---|
| bullet | 278.5 | 357.2 | 0.694 |
| **blitz** | **277.3** | **355.9** | **0.718** |
| rapid | 267.5 | 345.2 | 0.689 |
| classical | 210.6 | 269.1 | 0.571 |

Порівняно з baseline-моделлю, що завжди передбачає середній Elo вибірки: MAE
583.8, R² ≈ 0 (`results/model_comparison.csv`).

## Ключові наукові знахідки

**1. Зміщення прогнозу "700 → 1600" та його виправлення калібруванням.**
Модель, натренована на зміщеній (найактивніші гравці) вибірці, регресує
передбачення до середнього: гравець з реальним Elo ≈678 отримував прогноз
**1337.7** (bias +659.8); гравець ≈2403 — заниження до 1956.6. Стратифікований
збір скорочує це зміщення (≈678→**913.6**), а подальше ізотонічне калібрування
(fit виключно на train-фолдах CV, leakage-free) — додатково (≈678→**876.0**).
Сумарно MAE на нижньому кінці рейтингу (<1100 Elo) впало **529.6 → 276.2
(-43%)**. Див. `results/fig_calibration.png`, `results/calibration_by_band.csv`.

**2. Ознаки engine-agreement (MultiPV) несуть основний сигнал.**
Адитивна абляція: базові 21 ознака → R²=0.691, MAE=291.1; +win-probability (3
ознаки) → R²=0.695, MAE=289.0 (майже нейтрально); **+engine agreement (5
ознак) → R²=0.718, MAE=277.3** (Δ=-13.8 MAE). Найсильніші за кореляцією з Elo:
`opening_acpl` (ρ=-0.61), `avg_move_rank` (ρ=-0.57), `acpl` (ρ=-0.56),
`top3_agree` (ρ=+0.54). `results/ablation_additive.csv`,
`results/fig_feature_groups.png`.

**3. Крива навчання вирівнялась — система signal-limited, не data-limited.**
R² зростає з 0.573 (100 гравців) до 0.718 (2160 гравців), але нахил хвоста
становить лише +0.010 R² на +1000 гравців (`results/learning_curve.json`,
вердикт `"FLATTENED … signal-limited, not data-limited"`). Це означає:
подальше нарощування вибірки дає спадну віддачу — пріоритет варто віддавати
новим ознакам, а не новим гравцям.

**4. Наївний `argmin` по SHAP дає відтворювану, але непридатну відповідь — і чому.**
Правило "слабкість = ознака з найбільшим від'ємним внеском" **відтворюване**:
split-half згода 0.413 проти випадкової 0.142, κ=0.314 [0.297; 0.330] (кластерний
бутстреп по гравцях, 21 590 розбиттів). Але **неінформативне**: збіг із
розрахунком за відхиленнями лише 0.052 при тривіальному орієнтирі "завжди називай
найпоширенішу категорію" 0.105 — тобто **вдвічі гірше за нетреноване правило**,
κ=0.009. Причина видна в розподілі відповідей: `avg_think_time` отримує 27%
усіх, `opening_acpl` 19%, `think_time_consistency` 14% — чотири ознаки збирають
понад 70%.

Дві причини встановлено кількісно:

1. **Внески не зіставні за амплітудою.** `opening_acpl` має найбільший `xgb_gain`
   (0.298), тож її внески систематично найбільші за модулем — `argmin` знаходить
   найгучнішу ознаку, а не найгіршу.
2. **Внесок вимірюється відносно середнього гравця всієї вибірки.** Гравець рівня
   900 від'ємний майже за всіма ознаками, тож мінімум указує на ту саму ознаку для
   всього рівня.

**Виправлення (`--rule standardised`, воно ж у продакшні):** кандидати обмежено 17
ознаками, яким відповідає тренувальна тема, а кожен внесок нормовано на його
типове значення для гравців того самого прогнозованого рівня. Результат на пулі
blitz, 2159 гравців:

| Показник | наївне | виправлене |
|---|---|---|
| кандидатів | 29 | 17 |
| випадковий рівень | 0.034 | 0.059 |
| тривіальний орієнтир | 0.105 | 0.134 |
| split-half згода | 0.413 | 0.108 |
| κ split-half | 0.314 | 0.045 |
| перетин трійок між половинами | 0.85 | 0.58 |
| збіг із розрахунком за відхиленнями | 0.052 | **0.286** |
| той самий збіг серед трьох названих | 0.144 | **0.493** |
| κ збігу | 0.009 | **0.238** |

Реплікується на всіх 4 пулах (7 483 гравці): збіг 0.185–0.286 при орієнтирі
0.111–0.135, тобто **1.7–2.1× вище**, тоді як наївне правило не перевищує орієнтир
у жодному пулі. Дзеркально κ відтворюваності падає до 0.038–0.066 скрізь.

**Компроміс справжній, не артефакт.** Перевірено дві альтернативні причини падіння
відтворюваності, обидві відкинуто: (а) дискретність рейтингових діапазонів —
половини партій одного гравця потрапляють у різні біни в 57% випадків, але заміна
на неперервну інтерполяцію змінює κ лише 0.042→0.045; (б) нестабільність самих
ознак — усі 17 кандидатів відтворюються між половинами з кореляцією 0.55–0.86,
тобто шум вносить крок атрибуції, а не вимірювання. Часткова стандартизація
(α між 0 і 1) дає монотонну криву без оптимуму — проміжної точки, кращої за обидва
краї, немає.

**Чому шортліст із 3, а не 1.** Дисперсія зосереджена в **порядку** близьких
кандидатів, а не в тому, які області взагалі потрапляють угору: half-split дає
той самий набір проблем, переставляючи сусідів. Тому `predict_and_explain(k=3)`
і `get_plan()`. Це піднімає обидві метрики виправленого правила (0.108→0.580 і
0.286→0.493), хоча наївне лишається відтворюванішим за будь-якого k.

**Застереження до числа 0.286.** Еталон — це правило за відхиленнями значень
ознак, а SHAP для ансамблів дерев приблизно монотонний за цими значеннями. Тобто
частину приросту дає зближення механізму з еталоном, а не покращення виявлення.
Незалежна перевірка — синтетична ін'єкція (знахідка 6), де правильна відповідь
задана наперед, — показує **скромніший** виграш: 3 категорії з 7 замість 2 за
першою відповіддю і однакові 3, якщо дивитися трійку. Реальні здобутки
виправлення — два: знята структурна сліпота до `blunder_rate` (+0.41 проти 0.00,
див. знахідку 6) і змістовність рекомендації, бо серед кандидатів більше немає
ознак без тренувальної теми. До виправлення троє реальних гравців рівнів 838,
1468 і 2315 усі отримували "середній час на хід" і тему `long`; після — "небезпека
для короля", "точність в ендшпілі", "точність у міттельшпілі"
(`results/worked_examples.csv`).

**5. Розглянута, але не прийнята альтернатива агрегації.**
`aggregation_methods.py` показує, що `mean+std` (58 вимірів: середнє + std на
ознаку) дає дещо кращий R² (0.896 проти 0.889 для звичайного `mean`), але
подвоює розмірність вектора для приросту ~0.007 R². Оскільки це вимагало б
іншої архітектури (тренування на агрегованих, а не пооб'єктних рядках),
застосунок залишає `mean` — прийнятний, добре обґрунтований компроміс.

**6. Чутливість синтетичної перевірки треба читати проти базового рівня.**
`synthetic_validation.py` (80 партій, по 20 у діапазонах 1000–1400/1400–1800/
1800–2200/2200–3000 Elo, глибина 12, критерій ін'єкції — падіння ймовірності
виграшу ≥10%) псує одну категорію й перевіряє, чи назве її SHAP. Сама по собі
чутливість оманлива: детектор має власну схильність називати певні ознаки й на
НЕПОГІРШЕНИХ партіях. Порівняння з цим рівнем змінює картину:

| категорія | чисті | після погіршення | приріст |
|---|---|---|---|
| Opening ACPL | 0.24 | **0.91** | **+0.68** |
| Middlegame ACPL | 0.29 | **0.62** | **+0.34** |
| Defensive ACPL | 0.35 | 0.31 | **−0.04** |
| Hanging-Piece | 0.10 | 0.01 | **−0.09** |
| Endgame ACPL | 0.01 | 0.00 | −0.01 |
| Blunder Rate | 0.01 | 0.01 | 0.00 |
| Advantage Conversion | 0.00 | 0.00 | 0.00 |

Тобто **Defensive 0.31 — це не часткове виявлення, а нуль**: на чистих партіях
детектор називає захист навіть частіше (0.35). Реальний приріст мають лише дві
категорії з семи. Загальна чутливість 0.27 при chance 0.14, але її 95% CI
(0.05–0.53) отримано ресемплінгом КАТЕГОРІЙ, тож ширина міряє розкид між ними,
а не точність середнього. Між діапазонами Elo картина не змінюється (0.25–0.31),
тож обмеження властиве механізму, а не вибірці.
`results/synthetic_validation_bands.json`.

Той самий експеримент під виправленим правилом (`--rule standardised`,
`results/synthetic_validation_bands_std.json`) змінює картину нерівномірно:

| категорія | наївне (приріст) | виправлене |
|---|---|---|
| Opening ACPL | **+0.68** | +0.31 |
| Middlegame ACPL | **+0.34** | +0.12 |
| **Blunder Rate** | **+0.00** | **+0.41** |
| Endgame / Conversion / Defensive / Hanging | ≤ 0 | ≤ 0 |

Головне тут `blunder_rate`: наївне правило не виявляло цю категорію **ніколи** —
її внески малі за амплітудою, тож у `argmin` вона не потрапляла, хай як сильно її
псували (знахідка 8). Виправлення знімає цю сліпоту структурно. Ціна — слабше
виявлення "гучних" категорій. Разом 3 категорії з 7 замість 2, а 95% CI загальної
чутливості звужується з [0.048; 0.532] до [0.089; 0.366]. **При k=3 різниці немає:
обидва правила покривають ті самі 3 категорії** — тобто перевага виправлення
проявляється насамперед тоді, коли називається одна відповідь.

**7. Ін'єкція не локальна — це занижує чутливість для blunder_rate.**
`synthetic_specificity.py` (20 партій) міряє, як після погіршення однієї
категорії зсуваються всі сім ознак, у стандартних відхиленнях пулу. Цільова
ознака **ніде не домінує чисто**: найкраще відношення власного зсуву до
найбільшого супутнього — 1.9 (opening), а в трьох випадках із семи супутній
зсув більший. Найгірший випадок — `blunder_rate`: за побудовою (`_eligible`
завжди True) підміна псує ходи в усіх фазах, тож endgame_acpl зсувається на
2.61 SD проти 2.32 у самого blunder_rate. Наслідок: мітка "blunder" не є єдиною
правильною відповіддю, тому 0.01 занижує чутливість. Але атрактор це не
пояснює: детектор назвав opening_acpl (зсув 1.35 SD), а не найсильніше зсунутий
endgame_acpl (2.61 SD). Протилежна проблема в `defense_acpl`: власний зсув лише
0.11 SD — маніпуляція там надто слабка.
`results/synthetic_specificity.json`.

**8. Нулі не пояснюються слабкою ін'єкцією (дозовий контроль).**
Погіршення посилено втричі (`--rate 1.0 --wp-lo 0.30`, 20 партій, 5 категорій
без приросту). Ін'єкція справді стала сильнішою (endgame_acpl +108.8 сп проти
+90.9; 39 підмінених півходів проти 25), але приріст над базовим рівнем лишився
нульовим у всіх п'яти: Defensive 0.50 при базі 0.50, Hanging 0.00 при 0.10,
Endgame/Conversion/Blunder 0.00 при 0.00.
`results/synthetic_validation_highdose.json`.

**9. Три шари обмеження: coverage@k.**
Замість однієї названої ознаки розглянуто k найслабших, із тим самим порівнянням
проти чистих партій (у дужках — приріст):

| категорія | @1 | @2 | @3 |
|---|---|---|---|
| Opening ACPL | 0.91 (+0.68) | 0.91 (+0.66) | 0.91 (+0.65) |
| Middlegame ACPL | 0.62 (+0.34) | **0.94 (+0.46)** | 0.96 (+0.43) |
| Blunder Rate | 0.01 (+0.00) | 0.40 (+0.29) | **0.86 (+0.65)** |
| Endgame ACPL | 0.00 (−0.01) | 0.14 (−0.06) | 0.41 (−0.09) |
| Defensive ACPL | 0.31 (−0.04) | 0.34 (−0.09) | 0.38 (−0.14) |
| Advantage Conversion | 0.00 (+0.00) | 0.01 (−0.10) | 0.17 (−0.24) |
| Hanging-Piece | 0.01 (−0.09) | 0.03 (−0.40) | 0.12 (−0.44) |

**`blunder_rate` — не сліпа зона**: на третьому місці приріст +0.65, такий самий
як в opening на першому. Сигнал є у SHAP-значеннях, його викидає правило
`argmin`. Отже межі детектора тришарові: opening виявляється першою відповіддю;
middlegame і blunder — лише серед кількох найслабших; endgame, conversion,
hanging і defense не виявляються на жодній із перевірених глибин.

**10. Порядок атрибуції змінює якість у межах зони, але не її ширину.**
`synthetic_aggregate.py` (20 умовних гравців по 4 партії близького рейтингу, та
сама слабкість внесена в усі 4) порівнює пооб'єктний і агрегований порядок на
однакових оброблених партіях, кожен — проти власного рівня на чистих партіях:

| категорія | пооб'єктно (чисті) | агреговано (чисті) |
|---|---|---|
| Opening ACPL | 0.82 (0.25) **+0.57** | 1.00 (0.20) **+0.80** |
| Middlegame ACPL | 0.56 (0.28) **+0.29** | 0.85 (0.35) **+0.50** |
| Defensive ACPL | 0.31 (0.34) −0.03 | 0.05 (0.15) −0.10 |
| Endgame ACPL | 0.00 (0.00) +0.00 | 0.00 (0.05) −0.05 |
| Advantage Conversion | 0.00 (0.03) −0.03 | 0.00 (0.20) −0.20 |
| Blunder Rate | 0.01 (0.00) +0.01 | 0.00 (0.00) +0.00 |
| Hanging-Piece | 0.00 (0.11) −0.11 | 0.00 (0.05) −0.05 |

Агрегування **помітно підсилює виявлення там, де воно є** (opening +0.57→+0.80,
middlegame +0.29→+0.50), але **не створює його там, де його немає**: чотири
категорії лишаються на нулі за обох порядків. Загальна чутливість майже не
рухається (0.24→0.27) саме тому, що п'ять із семи категорій не додають нічого.
Увага: без порівняння з чистими партіями це читалося б інакше — "Defensive падає
0.31→0.05" виглядає втратою здатності, хоча приріст там від'ємний в обох
порядках, тобто виявлення не було з самого початку.
`results/synthetic_aggregate_wide.json`.

## Зовнішня валідація: Chess.com

Мотивація: користувач, що тестував систему на власному профілі Chess.com,
повідомив про стабільно завищений прогноз. Оскільки модель тренована виключно
на Lichess, потрібно було кількісно відокремити (A) відоме залишкове зміщення
моделі від (B) різниці рейтингових шкал платформ — і, якщо можливо, виправити
другу причину.

**Методологія збору Chess.com-семплу.** Chess.com не публікує bulk-дамп партій
(на відміну від Lichess), тому `collect_crossplatform.py` збирає дані через
публічний API: кожна отримана партія містить нік і рейтинг суперника, тож BFS
по суперниках від кількох seed-акаунтів відкриває нових гравців без
завантаження повної бази. Гравці зберігаються лише коли потрапляють у
недозаповнений рейтинг-бін (стратифікація 400–2800, крок 200, по 9 гравців на
бін). Зібрано три пули: bullet, blitz, rapid (classical на Chess.com немає).

**Знахідка методології — обхід по суперниках структурно не досягає країв
шкали.** Підбір суперників зводить близьких за рейтингом, тож пошук лишається
в діапазоні, з якого почався. У bullet це видно найчіткіше: за 3830 запитів
заповнено всі біни нижче 2000, але знайдено **лише одного** гравця вище 2200,
а 43% зустрінутих мали рейтинг нижче 400 (медіана 439).

Виправлено `seed_by_rating.py` — цільовим відбором seed-акаунтів. Публічні
списки титулованих гравців (`/pub/titled/{GM,IM,FM,NM,CM,W*}`) і гравців за
країнами (`/pub/country/{ISO}/players`) дають кандидатів поза досяжністю
обходу, а `/pub/player/{u}/stats` повертає поточний рейтинг — тобто кандидат
перевіряється **одним дешевим запитом**, без вивантаження партій. Один прохід
`--pool all` обслуговує всі три пули, бо `/stats` віддає рейтинг одразу для
кожного. За 3114 перевірок відібрано по 120 seed-акаунтів на пул, по 10 на бін;
після цього всі 12 бінів заповнено в кожному пулі.

**Застереження про склад верхнього біна rapid.** Сильних гравців у rapid
фізично мало, тому бін 2600–2800 добрано з публічного рейтингового списку
(`/pub/leaderboards`): 6 із 9 гравців у ньому належать до світової першої
півсотні за цим контролем. У решті бінів такого зміщення до професійного
рівня немає.

| пул | гравців | партій | діапазон Elo |
|---|---|---|---|
| bullet | 108 | 1 266 | 419–2751 |
| blitz | 108 | 1 259 | 432–2771 |
| rapid | 108 | 1 262 | 418–2796 |

**Частина A — наскільки завищено, і чому.** Порівняння зміщення (прогноз −
факт) на двох групах, обидві через *точно той самий* живий пайплайн
(`EngineAnalyzer(time_limit=0.05)`, заморожена модель відповідного пулу).
Контрольна група Lichess набрана тією ж стратифікацією, по 5 гравців на бін
(`--per-bin 5` → 57/57/50 гравців).

**Порівнювати середні по групах не можна.** Зміщення круто спадає з рейтингом
(регресія до середнього), а рейтинговий склад вибірок різний — у rapid семпл
Chess.com на 206 Elo сильніший за контрольну групу. Сильніша вибірка занижує
власне середнє й **маскує розрив**: сире порівняння дає для rapid лише +49
(p=0.385), хоча розрив там є. Тому `rating_adjusted_gap()` підганяє
`bias ~ platform * rating` і читає вертикальну відстань між прямими на
фіксованих рівнях. Взаємодія значуща в усіх пулах (p=0.009 / 0.002 / 0.002),
тобто розрив **залежить від рівня гри**:

| пул | сире середнє (L / CC) | @800 Elo | @1500 | @2200 |
|---|---|---|---|---|
| bullet | +135 / +371 | **+345** | +225 | +106 (н/з) |
| blitz | +154 / +351 | **+316** | +203 | +90 |
| rapid | +222 / +271 | **+259** | +132 | +5 (н/з) |

Шкали розходяться найсильніше у слабких гравців і практично збігаються вгорі:
Chess.com дає **менше** пунктів за ту саму силу гри, і тим менше, чим слабший
гравець. `results/fig_external_validation_bias.png` (по пулах).

**Увага:** бік Lichess перераховується рушієм щоразу з часовим лімітом 0.05 с,
тож між прогонами прогноз окремого гравця коливається на 23–31 Elo у
середньому (до 135 на окремому гравці), тоді як групові середні тримаються в
межах 2 Elo — див. відомі обмеження.

**Частина B — рекалібрування.** K-fold (5), leakage-free; калібрувальна функція
"сирий прогноз (шкала Lichess) → рейтинг Chess.com" підганяється виключно на
Chess.com-семплі, сама модель лишається замороженою:

| пул | сирий MAE | ізотонічна | лінійна | зниження | зміщення після |
|---|---|---|---|---|---|
| bullet | 483.3 | **348.4** | 339.0 | −28% | −4.9 |
| blitz | 409.4 | **238.3** | 251.2 | −42% | +2.4 |
| rapid | 388.4 | **253.9** | 248.5 | −35% | −3.6 |

**Ізотонічну зафіксовано для всіх пулів, а не обрано за меншим MAE.** Різниця
між нею й лінійною становить 2–5% похибки, її bootstrap-CI перетинає нуль в
усіх трьох пулах, а на 20 інших випадкових розбиттях "переможець" змінюється
18/20 разів у bullet і 16/20 у rapid — тобто вибір за MAE слідував би за seed
перехресної перевірки. Натомість залишки лінійної підгонки зберігають
систематичний вигин у **кожному** пулі, тож саме припущення лінійності
суперечить формі зв'язку. Усереднено по пулах методи нерозрізненні (MAE 280.2
проти 279.6), отже фіксація гнучкішого монотонного методу нічого не коштує.

Фінальні функції, підігнані на всіх 108 гравцях кожного пулу, збережені в
`src/ml/models/chesscom_recalibration_{bullet,blitz,rapid}.pkl` і
**автоматично застосовуються в `app.py`**, коли партії отримано з Chess.com.
Для classical функції немає — такого контролю на Chess.com не існує, тож
`app.py` показує прогноз у шкалі Lichess із дисклеймером.

## Відомі обмеження

- **Швидкість аналізу.** Дані для тренування та прогнози в `app.py` рахуються
  при `time_limit=0.05с/хід` (не фіксована глибина) — це узгоджено між
  збором даних і інференсом, але є неглибоким і трохи шумним аналізом.
  `synthetic_validation.py` натомість використовує фіксовану глибину 12 —
  глибший і відтворюваніший, але лише для контрольованого експерименту, не для
  продакшн-моделі.
- **Шкала рейтингу — лише Lichess.** Прогноз відповідає рейтинговій шкалі
  Lichess; рейтинги інших платформ систематично відрізняються. Кількісно
  підтверджено в [Зовнішній валідації](#зовнішня-валідація-chesscom) на 324
  гравцях Chess.com: розрив залежить від рівня гри й сягає +345/+316/+259 Elo
  (bullet/blitz/rapid) у слабких гравців, а до 2200 Elo зникає в bullet і
  rapid. Виправлено калібрувальними функціями для трьох пулів
  (−28…−42% MAE); для classical такого контролю на Chess.com немає.
- **Час аналізу не фіксовано, тож окремий прогноз не відтворюється точно.**
  Бюджет рушія заданий часом (0.05 с/позиція), а не глибиною, тож за
  повторного аналізу тих самих партій прогноз коливається на 23–31 Elo у
  середньому (до 135 на окремому гравці). Групові оцінки при цьому стійкі:
  середнє зміщення між прогонами змінюється не більш ніж на 2 Elo. Це ~10% від
  власної похибки моделі й пояснює, чому в контрольованих експериментах
  (`synthetic_*`) використано фіксовану глибину 12.
- **Тонкі хвости розподілу залишаються.** Навіть після стратифікації дуже
  низькі (<800) і дуже високі (>2300) рейтинги — рідкісні в реальних даних
  Lichess, тож калібрування на екстремумах — найменш надійне. У classical це
  властивість самої популяції, а не відбору: `pool_population.py` (скан 400 тис.
  партій, без жодної фільтрації) показує, що класику грають майже виключно
  гравці середнього рівня — нижче 1000 Elo припадає 2.6%, вище 2200 — 1.6%,
  тоді як діапазон 1200–2000 охоплює 83%. Сама класика становить ~0.5% дампу.
- **Поріг «≥8 партій» відсікає більшість гравців.** Колектор бере лише тих, хто
  має щонайменше 8 партій у пулі за місяць. На скані 300 тис. партій це 13.6%
  гравців blitz, які, втім, дають 46.3% партій: кожен третій гравець за місяць
  зіграв рівно одну партію. Модель відтак калібрована на регулярних гравцях, а
  не на всій популяції платформи.
- **Невідповідність train/inference.** Модель тренується на векторах ознак
  ОДНІЄЇ партії, а `app.py` на інференсі усереднює вектори N партій. Це
  свідомий вибір, обґрунтований `aggregation_curve.py`/`learning_curve.py`
  (агрегація суттєво знижує шум), але є архітектурною відмінністю, яку варто
  проговорити явно.
- **Мультиколінеарність.** Кілька ACPL-похідних ознак сильно корелюють
  (VIF(`acpl`)=44.4, VIF(`avg_move_rank`)=30.8, `results/vif.csv`) — очікувано
  для дерев (XGBoost стійкий до цього для прогнозу), але ускладнює
  інтерпретацію ІНДИВІДУАЛЬНИХ SHAP-внесків корельованих ознак.
- **Правило вибору напряму — компроміс, а не оптимум.** Наївний `argmin`
  відтворюваний (κ=0.31), але не інформативніший за "завжди називай найпоширенішу
  категорію"; нормоване правило вдвічі перевершує цей орієнтир, але його κ падає до
  0.04 на 4 партіях. Обрано друге (знахідка 4), бо стабільно повторювана
  неінформативна відповідь для рекомендації нічого не варта — але це вибір, а не
  перевага за всіма критеріями. Шортліст із 3 напрямів частково знімає компроміс.
- **Нормування потребує популяційного довідника.** Один гравець не дає статистик
  свого рівня, тому `shap_reference_<pool>.pkl` рахується наперед на навчальній
  вибірці. Без нього `model.py` відкочується на сирий `argmin` (поле
  `weakness_rule` це показує). Довідник треба перебудовувати після кожного
  перетренування моделі.
- **Детектор слабкості працює лише для частини категорій.** Знахідки 6–9
  дають тришарову картину: `opening_acpl` виявляється першою відповіддю
  (приріст +0.68 над базовим рівнем); `middlegame_acpl` і `blunder_rate` —
  лише якщо дивитися кілька найслабших ознак (+0.46 при k=2 і +0.65 при k=3);
  `endgame_acpl`, `conversion_acpl`, `hanging_rate` і `defense_acpl` не
  виявляються на жодній перевіреній глибині й за втричі сильнішого погіршення.
  Причина — домінування ознак за амплітудою внеску плюс колінеарність:
  `opening_acpl` має найбільший `xgb_gain` (0.298) і сильно корелює з рештою
  ACPL-похідних. У поєднанні з Experiment B (знахідка 4) це означає, що
  рекомендації пазлів обґрунтовані для позиційних категорій, а для тактичних
  потребують або показу кількох кандидатів, або ознак із меншим перекриттям.
- **Показники детектора не можна читати без базового рівня.** Детектор має
  власну схильність називати певні ознаки навіть на непогіршених партіях
  (`defense_acpl` — 0.35, `middlegame_acpl` — 0.29). Будь-яка "чутливість"
  без віднімання цього рівня завищена: приклад — Defensive 0.31, що виглядає
  частковим успіхом, а насправді нижче власного базового рівня.

## Встановлення та запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export STOCKFISH_PATH=/opt/homebrew/bin/stockfish   # або де встановлено Stockfish

streamlit run app.py
```

Треновані моделі (`src/ml/models/xgboost_elo_<pool>.json`) уже включені; для
перетренування на нових даних — див. таблицю відтворення результатів вище.
